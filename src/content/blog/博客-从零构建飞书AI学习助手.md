# 从零构建一个飞书 AI 学习助手：用 22 小时把想法变成产品

> 一个测试工程师的 AI 辅助开发实战记录——从需求澄清到 7 个迭代阶段，用 TDD 方式交付一个能听懂人话的飞书智能体。

---

## 缘起：一个"手工活"痛点

我是一名测试工程师，业余时间在学 AI 测试。学习过程中遇到几个很实际的麻烦：

- **记录靠手记**：今天学了什么、花了多长时间，全靠自己打开多维表格手动填
- **笔记散落**：零散的想法、踩坑记录散落在聊天记录里，想整理的时候找都找不到
- **忘记打卡**：经常学到一半就忘了记录，一周下来表格空空如也
- **效果无从验证**：学完不知道自己掌握了多少

有没有可能，让一个机器人替我做这些事？发一句话它就自动帮我记、帮我整、帮我提醒、帮我出题？

于是我决定做一个**飞书 AI 学习助手**。

---

## 第 0 步：先想清楚"做成什么样"

在写一行代码之前，花时间把需求想清楚是值得的。我用了一套结构化方法：

### 一句话定义

> 一个飞书 AI 智能体，能听懂自然语言指令，自动记录学习进度到多维表格、安排日历日程、主动提醒学习、归纳零散笔记为结构化文档，并能出题评估学习效果和推荐资源。

### 用户故事驱动

把核心场景用"作为...我想要...以便..."的格式写下来：

| 编号 | 用户故事 |
|------|---------|
| US-001 | 作为学习者，我想把学习计划文件发给机器人后自动生成任务和日程，以便不用手动排期 |
| US-002 | 作为学习者，我想日常学习记录被自动识别并记入多维表格，以便随时可查学习轨迹 |
| US-003 | 作为学习者，我想未打卡时收到提醒，以便不中断学习节奏 |
| US-004 | 作为学习者，我想一键将本周零散记录归纳成结构化文档，以便回顾和输出 |
| US-005 | 作为学习者，我想自动出题测试学习效果，以便知道自己掌握了多少 |
| US-006 | 作为学习者，我想获得学习资源推荐，以便知道下一步学什么 |

### 验收标准（AC）先行

每条用户故事拆成可验证的验收标准，总共 20 条。比如：

> **AC-003**：Given 用户发送了包含学习内容的消息，When 机器人智能判断为学习记录，Then 自动在多维表格新增一行（日期、内容摘要、耗时、主题分类、状态），不重复记录。

> **AC-007**：Given 用户重复发送了已记录过的学习内容，When 机器人判断为重复，Then 提示"这条看起来和之前记录的内容很像，需要我重复记录吗？"，等待确认后再写入。

有了明确的 AC，后面的开发和测试就有了目标——每一行代码都在"兑现"某条 AC。

## 技术设计：4 个关键决策

需求定了之后，做技术设计时有几个选择很关键。

### 决策 1：意图分类——规则 + LLM 混合

用户消息可能是学习记录，可能是"考考我"，也可能是随意闲聊。怎么区分？

一开始想过纯关键词匹配，但太容易误判。"我学到了做人要善良"明显不是技术学习，但包含"学到了"这个关键词。

最终选了**混合策略**：命令触发词（"考考我"、"整理笔记"、"推荐资源"、"帮我制定"）走规则快速路由，零 API 调用；未命中的消息交给 LLM 分类，判断是学习记录还是闲聊。模糊情况倾向不记录（宁缺毋滥）。

### 决策 2：SQLite 存元数据，飞书存学习数据

应用配置（Base ID、提醒时间）和会话状态（出题答题上下文、重复确认等）需要存储。有两个选择：全存飞书多维表格，或本地 SQLite。

飞书多维表格每次读写都要调 API，有延迟和 QPS 限制——而会话状态（比如等待用户答题）需要高频读写。所以选了本地 SQLite 存元数据和会话状态，学习记录本体存在飞书（用户可见、可手动编辑）。

### 决策 3：先本地提取文本，再交给 LLM

用户上传的学习计划文件可能是 Markdown、Word、TXT。如果直接把原始文件扔给 LLM，排版标记会干扰提取效果。

所以先本地转纯文本（`python-docx` 处理 Word，内置读取处理 Markdown/TXT），再交给 LLM 做结构化提取。LLM 输入干净，token 消耗也可控。

### 决策 4：飞书 3 秒必须返回 200 的硬约束

飞书事件回调要求在 3 秒内返回 HTTP 200，否则会重试。但 LLM 调用和飞书 API 操作加起来远超 3 秒。

所以 **Webhook 接收和业务处理严格解耦**：收到消息后立即验签并返回 200，所有耗时操作（LLM 调用、飞书 API）全部异步执行，完成后通过 `im.message.create` API 回复用户。

### 架构一览

```
消息流：
用户 → 飞书 → POST /webhook → 验签 + 3秒内返回200
                                    ↓ (异步)
                              Intent Router
                           (规则命中 / LLM分类)
                                    ↓
              ┌─────────────────────┼─────────────────────┐
              ↓                     ↓                     ↓
     LearningRecord         NoteHandler            QuizHandler
     (提取→去重→写Base)    (汇总→归纳→出文档)    (出题→批改→写结果)
              
模块划分：
- Webhook Receiver    → 接收飞书事件
- Intent Router       → 意图分类 + 路由
- 7 个 Handler         → 业务逻辑
- LLM Service         → 统一 LLM 调用封装
- Feishu Service      → 飞书 API 封装（Base/Doc/Calendar/Message）
- Storage Service     → SQLite 读写
- Scheduler           → 每日提醒定时任务
```

## 开发过程：7 个阶段，TDD 驱动

整个工程拆成了 7 个阶段、17 个任务，预估 22 小时。每个任务按 **RED → GREEN → REFACTOR** 循环推进：

1. **先写测试**（RED）——把验收标准翻译成测试用例
2. **写最少代码让测试通过**（GREEN）——不提前做任何"以后可能用到"的设计
3. **重构**（REFACTOR）——消除重复、改善结构，测试必须保持全绿

### 阶段 0：基础设施（5 个任务）

先把骨架搭起来。项目脚手架、SQLite 存储、LLM 调用封装、飞书 API 封装（含 token 自动管理和缓存）、Webhook 接收器（验签 + 去重 + 3 秒返回）。

这一步没有业务 AC，但它决定了后续所有阶段能不能顺畅开发。碰到几个坑：

- FastAPI 路由参数缺少类型注解，框架把它当查询参数解析，返回 422
- 测试环境初始化时缺少 `.env` 文件导致导入失败，需要在 conftest 预设变量
- Webhook 签名验证一开始写了 `return True` 的占位实现，测试当然全过但没意义，后续补上真正的 HMAC-SHA256 验证

**教训**：基础设施阶段的测试要真正验证"链路通了"，Mock 要用得克制——该调真实 API 的就得调，否则绿了也没意义。

### 阶段 1：初始化 + 学习记录（4 个任务）

这是用户感知最强的阶段。实现四个能力：

1. **首次初始化**（AC-001）：用户发第一句话时，自动创建学习多维表格（6 列：日期、内容、耗时、主题分类、完成状态、笔记链接）和文档文件夹
2. **意图路由**（AC-006, AC-011）：5 组命令触发词（考考我/整理笔记/推荐资源/帮我制定/上传文件）+ LLM 兜底分类
3. **学习记录提取与写入**（AC-003, AC-013）：LLM 从自然语言中提取 {主题, 耗时, 摘要}，写入 Base
4. **重复检测**（AC-007）：查询近一周记录 → LLM 比对相似度 → 相似则设置 `awaiting_dup_confirm` 状态，询问用户

这里碰到了一个有趣的 bug：触发词匹配用了 `all(kw in message)`，但用户消息不可能同时包含一个集合里的所有备选关键词。改成 `any(kw in message)` 后全部通过。

**教训**：逻辑 bug 的根源往往在"直觉假设"——写 `all` 的时候直觉上觉得"这些关键词应该都匹配"，但忘了集合里的词是"或"关系不是"且"关系。

### 阶段 2：学习计划管理（3 个任务）

让机器人能处理学习计划：

- **文件导入**（AC-002, AC-008）：下载文件 → 提取文本 → LLM 解析计划项 → 写入 Base（状态="计划中"）→ 创建日历日程
- **日历冲突**（AC-010）：创建日程前先查空闲/忙碌，冲突时询问用户
- **计划自动生成**（AC-019, AC-020）：用户没文件时，根据目标（如"2 个月掌握 AI 自动化测试"）自动生成分阶段计划，输出飞书文档，采纳后同步 Base + Calendar

### 阶段 3：每日学习提醒（1 个任务）

APScheduler 在进程内注册定时任务，按 `app_config` 里的 `reminder_time`（默认 20:00）触发。查当日 Base：有计划中任务但无已完成记录 → 发提醒消息。飞书消息通道自动覆盖移动端推送，无需额外配置。

逻辑其实很简单，但 AC 覆盖了 5 种情况（有计划无完成/有完成/无计划有记录/无计划无记录/时间可配置），测试用例正好对应这 5 种，写完测试再写代码，一条条点亮。

### 阶段 4：笔记整理（1 个任务）

"帮我整理这周的笔记"——查本周 Base 记录 → 判空 → LLM 按主题分组归纳 → 创建飞书文档 → 链接写回 Base 的"笔记链接"列。

LLM prompt 设计是这里的关键：要让它按主题聚合而不是按时间排列，要过滤碎片闲聊，同类内容合并。prompt 里加了具体约束和输出格式示例后，效果才稳定。

### 阶段 5：学习效果测试（2 个任务）

多轮对话状态机在这里真正起作用：

1. **出题**（AC-014）：查本周记录 → LLM 生成 3-5 道题 → 答案存在 `session_state.context` 里不发给用户 → 设置状态 `awaiting_quiz_answer`
2. **批改**（AC-015）：用户作答 → LLM 逐题批改 → 返回正确率 + 薄弱知识点 → 写入 Base → 状态恢复 idle

状态机保证了答题过程中不会被其他消息干扰——处于 `awaiting_quiz_answer` 时发学习记录会被提示"请先完成测试"。

### 阶段 6：资源推荐（1 个任务）

基于学习主题和薄弱点推荐 2-3 个资源，用户标记"已看"后记入 Base，下次不重复推。

## 几个重要的反思

### 1. 需求澄清是回报最高的投入

写 AC 的时候觉得"是不是太细了"，但到了开发阶段，每一条 AC 直接变成测试用例的 Given-When-Then 模板，写测试几乎不用动脑子。20 条 AC → 60+ 测试用例，映射关系清清楚楚。

反过来想，如果一开始没写 AC，很多边界情况（比如"无记录时不创建空文档"、"日历冲突时询问用户"）大概率会在开发后期才发现，返工成本高得多。

### 2. TDD 在 AI 项目中依然有效

有人觉得 AI 项目"行为不确定"，不适合 TDD。但我的体会是：**正是因为 AI 行为不确定，测试才更重要**。LLM 调用可以 mock，测试的是你的逻辑——判断结果、异常处理、状态流转——这些跟普通后端代码没有本质区别。

Mock LLM 返回"学习记录"和"闲聊"两种结果，就能测意图路由的完整分支。Mock LLM 返回"重复"和"不重复"，就能测去重逻辑。LLM 本身的输出质量不在单元测试范围内，那是 prompt 调优的事。

### 3. 规则 + LLM 混合是个好东西

纯 LLM 分类准确但每次都调 API，有延迟和成本。纯规则快但覆盖不全。混合策略取了两边的好处：90% 的明确命令走规则零成本直达，剩下 10% 的模糊意图才需要 LLM 介入。这在实际使用中体验很好——说"考考我"秒回，不用等着 API 返回分类结果。

### 4. 状态机是 Bot 的灵魂

Bot 不是无状态的 REST API。多轮对话——出题→作答→批改、重复检测→询问确认、日历冲突→询问处理——都需要记住"当前在哪一步"。

一开始想过用 Redis，但对于个人自用的场景太厚重了。SQLite 一张 `session_state` 表（user_id + state + context JSON）就够用，24h 过期自动清理，简单可靠。

## 如果你也想做一个

技术栈：
- **Python 3.10+** + FastAPI
- **飞书开放平台**（应用创建 + API 调用，权限 scope 要配对）
- **国内大模型 API**（DeepSeek / 通义千问，OpenAI 兼容协议）
- **SQLite**（本地元数据存储）
- **APScheduler**（定时任务）

建议的开发顺序：
1. 先把飞书应用创建好，拿到 App ID / App Secret
2. 搭好 Webhook 接收器，跑通"收到消息能回复"的链路（这个一步通了后面都是增量）
3. 从最简单的 Handler 开始（比如学习记录写入），跑通 LLM → 飞书 API 的完整链路
4. 再加复杂的状态机交互（出题、冲突处理等）
