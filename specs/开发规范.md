# 开发规范

本文档定义「数字花园博客」项目的代码风格、命名约定、Git 工作流和 AI 协作协议，确保代码库长期可维护。

---

## 1. 语言与运行时要求

| 维度 | 规格 |
|------|------|
| **语言** | TypeScript 5.x，全栈统一 |
| **运行时** | Node.js >= 18.17（LTS） |
| **包管理器** | pnpm >= 8.0（禁止使用 npm / yarn） |
| **严格模式** | `tsconfig.json` 中 `strict: true`，禁止 `any`（特殊情况须 `// eslint-disable-next-line @typescript-eslint/no-explicit-any` 注释理由） |

## 4. TypeScript 特定规范

### 4.1 类型导入

必须使用 `import type` 导入仅作类型使用的声明：

```typescript
// ✅ 正确
import type { Article } from "../types";

// ❌ 错误
import { Article } from "../types";
```

### 4.2 `type` vs `interface`

| 场景 | 偏好 | 原因 |
|------|------|------|
| 对象形状（组件 Props、Frontmatter） | `interface` | 可扩展、错误信息更清晰 |
| 联合类型、交叉类型、工具类型 | `type` | `interface` 无法表达 |
| 函数签名 | `type` | 更简洁，支持重载 |

```typescript
// ✅ 对象形状用 interface
export interface ArticleFrontmatter {
  title: string;
  date: Date;
  category: string;
  tags: string[];
}

// ✅ 联合类型用 type
export type Theme = "light" | "dark";

// ✅ 函数签名用 type
export type PostFilter = (post: Article) => boolean;
```

### 4.3 禁止的写法

```typescript
// ❌ 禁止：显式 any
function process(data: any): any { /* ... */ }

// ✅ 替代方案：使用 unknown + 类型守卫
function process(data: unknown): Result {
  if (!isValidData(data)) throw new Error("Invalid data");
  return transform(data);
}

// ❌ 禁止：非空断言（!）
const title = article!.title!;

// ✅ 替代方案：可选链 + 默认值
const title = article?.title ?? "Untitled";

// ❌ 禁止：@ts-ignore
// @ts-ignore
const result = unsafeOperation();

// ✅ 替代方案：@ts-expect-error（如果确实需要，必须注明原因）
// @ts-expect-error — Astro Content Collections 的类型推断在此处有延迟
const result = astroSpecificWorkaround();

// ❌ 禁止：enum（编译产物大，且与 tree-shaking 兼容性差）
enum PostStatus { Draft, Published }

// ✅ 替代方案：const assertion + type
const POST_STATUS = { Draft: "draft", Published: "published" } as const;
type PostStatus = (typeof POST_STATUS)[keyof typeof POST_STATUS];

// ❌ 禁止：隐式 any 的 catch 参数
try { /* ... */ } catch (e) { console.error(e.message); }

// ✅ 替代方案：显式标注 unknown
try { /* ... */ } catch (e: unknown) {
  const message = e instanceof Error ? e.message : "Unknown error";
  console.error(message);
}
```

### 4.4 空值处理

```typescript
// ✅ 使用可选链和空值合并，禁止深层嵌套的三元表达式
const displayName = post?.author?.name ?? "匿名";
const tags = post?.tags?.length ? post.tags : ["未分类"];
```

## 5. Astro 特定规范

### 5.1 组件设计原则

- **默认零 JS**：所有 `.astro` 组件不得包含客户端脚本。交互逻辑仅通过 Preact Island（`.tsx`）实现
- **布局嵌套**：页面不直接渲染 `<html>`、`<head>`、`<body>`，必须使用布局组件（`BaseLayout` / `BlogPostLayout`）
- **数据查询在页面层**：`src/pages/` 中的页面组件负责调用 `getCollection()`，通过 Props 向下传递数据，子组件不直接查询 Content Collections
- **单文件单一职责**：一个 `.astro` 文件只做一件事。如果 frontmatter 代码块超过 30 行，考虑抽取到 `src/utils/`

### 5.2 组件文件结构

```astro
---
// 1. Astro 内置导入
import { Image } from "astro:assets";

// 2. 布局导入
import BaseLayout from "../layouts/BaseLayout.astro";

// 3. 组件导入
import PostCard from "../components/PostCard.astro";

// 4. 工具/类型导入
import type { Article } from "../types";
import { getAllPosts } from "../utils/content";

// 5. 数据查询
const posts = await getAllPosts();
---

<!-- 6. 模板（HTML/Astro 组件） -->
<BaseLayout>
  <PostList posts={posts} />
</BaseLayout>
```

### 5.3 导入排序

按以下顺序分组，组间空一行：

```astro
---
// 1. Astro 运行时（astro:assets, astro:content）
// 2. 布局（../layouts/）
// 3. 组件（../components/）
// 4. 工具（../utils/）
// 5. 类型（../types/）
---
```

### 5.4 导出规则

- **Astro 组件**：不导出（组件即页面/模板，通过文件路径引用）
- **Preact 组件**：使用命名导出，禁止 `export default`

```tsx
// ✅ 正确
export function SearchBar() { /* ... */ }

// ❌ 错误
export default function SearchBar() { /* ... */ }
```

- **工具函数**：使用命名导出

```typescript
// ✅ 正确
export function formatDate(date: Date): string { /* ... */ }

// ❌ 错误
export default function formatDate(date: Date): string { /* ... */ }
```

### 5.5 页面数据获取模式

```astro
---
// ✅ 标准模式：页面层查询，通过 Props 传递
import { getCollection } from "astro:content";
import type { CollectionEntry } from "astro:content";

const posts = await getCollection("blog");
const sortedPosts = posts
  .filter((p) => !p.data.draft)
  .sort((a, b) => b.data.date.valueOf() - a.data.date.valueOf());
---

<PostList posts={sortedPosts} />
```

### 5.6 Content Collections 规范

`src/content/config.ts` 必须定义完整的 Zod Schema：

```typescript
import { defineCollection, z } from "astro:content";

const blogCollection = defineCollection({
  type: "content",
  schema: z.object({
    title: z.string().min(1).max(100),
    date: z.date(),
    updated: z.date().optional(),
    category: z.string().min(1),
    tags: z.array(z.string()).default([]),
    description: z.string().min(1).max(300),
    draft: z.boolean().default(false),
  }),
});

export const collections = { blog: blogCollection };
```

## 6. 样式规范

### 6.1 唯一样式方案

本项目使用 **TailwindCSS**，禁止使用 CSS Modules、styled-components 等方案。

**使用原则**：
- 优先使用 Tailwind 原子类，仅在以下情况写自定义 CSS（在 `global.css` 中）：
  - 代码高亮主题（Prism / Shiki）
  - 文章正文排版（`prose` 无法覆盖的细节）
  - 复杂的 `@keyframes` 动画
- 深色模式通过 `dark:` 前缀处理，策略为 `class`（`<html class="dark">`）
- 响应式断点使用 Tailwind 默认：`sm`(640px) → `md`(768px) → `lg`(1024px) → `xl`(1280px)

```astro
<!-- ✅ 正确：原子类组合，响应式 + 暗色模式一目了然 -->
<article class="prose prose-lg dark:prose-invert mx-auto px-4 sm:px-6 lg:px-8">

<!-- ✅ 正确：条件类名使用 clsx -->
<nav class={clsx("flex gap-4", isOpen && "block", !isOpen && "hidden")}>
```

### 6.2 禁止的样式写法

```astro
<!-- ❌ 禁止：内联 style 属性 -->
<div style="color: red; margin-top: 20px;">

<!-- ❌ 禁止：在 .astro 文件中写 <style> 块（除非有全局不可替代的理由） -->
<style>
  .my-custom-class { color: red; }
</style>

<!-- ❌ 禁止：使用 !important -->
<div class="text-red-500!">

<!-- ❌ 禁止：动态拼接原子类名（Tailwind 无法摇树优化） -->
<div class={clsx("text-" + color + "-500")}>

<!-- ✅ 替代方案：写完整类名 -->
<div class={clsx(color === "red" && "text-red-500", color === "blue" && "text-blue-500")}>
```

## 7. Git 工作流

### 7.1 分支策略

> 独立开发者，采用简化 Trunk-Based 模式。

```
main ─────●──────────●──────────●──────────●
           \          /            \
       feat/search  feat/theme    feat/archive
```

| 规则 | 说明 |
|------|------|
| **主分支** | `main`，始终可部署（GitHub Actions 自动部署） |
| **功能分支** | 从 `main` 分出，合并回 `main` |
| **直接提交** | 内容更新（新增/修改文章、修正笔误）可直接在 `main` 提交 |
| **合并方式** | Squash Merge（保持 `main` 历史线性、每条记录一个完整功能） |

### 7.2 分支命名规范

```
<type>/<short-description>
```

| 类型 | 用途 | 示例 |
|------|------|------|
| `feat/` | 新功能 | `feat/search-page`、`feat/tag-cloud` |
| `fix/` | Bug 修复 | `fix/theme-flicker`、`fix/mobile-layout` |
| `refactor/` | 重构 | `refactor/content-queries` |
| `chore/` | 构建/配置/依赖 | `chore/upgrade-astro` |
| `docs/` | 文档/文章 | `docs/add-astro-guide` |
| `style/` | 样式调整 | `style/improve-typography` |

### 7.3 提交信息规范 (Conventional Commits)

所有 Git 提交信息**必须**遵循 [Conventional Commits](https://www.conventionalcommits.org/) 格式：

```
<type>(<scope>): <subject>

[body]

[footer]
```

#### 类型 (type)

| 类型 | 说明 |
|------|------|
| `feat` | 新功能（用户可感知的变化） |
| `fix` | Bug 修复 |
| `refactor` | 重构（不改变功能行为） |
| `style` | 样式/格式调整（不改变逻辑） |
| `docs` | 文档/文章变更 |
| `test` | 测试相关 |
| `chore` | 构建工具/依赖/配置 |
| `perf` | 性能优化 |
| `ci` | CI/CD 配置 |

#### 作用域 (scope)

| scope | 对应范围 |
|-------|---------|
| `content` | 文章内容及 Content Collections Schema |
| `layout` | 布局组件（BaseLayout、BlogPostLayout 等） |
| `search` | 搜索功能（SearchBar、Pagefind 配置） |
| `theme` | 深色模式切换、主题样式 |
| `style` | 全局 CSS、TailwindCSS 配置 |
| `seo` | SEO 元标签、sitemap |
| `build` | 构建配置（astro.config、CI/CD） |
| `deps` | 依赖更新 |

#### 提交信息规则
- `subject`：中文或英文均可，但同一 commit 不得混用；首字母小写（英文）；不加句号；不超过 72 字符
- `body`：解释**为什么**这样改，不是重复标题；每行不超过 72 字符
- `footer`：关联 Issue 用 `Closes #N`

#### 示例

```
feat(search): 添加 Pagefind 全文搜索

Pagefind 在构建时扫描 dist/ 生成静态索引，零运行时依赖，
对比 Fuse.js 方案不需要前端加载全量 JSON，对文章量大时更友好。

Closes #3
```

```
fix(theme): 修复页面加载时深色模式闪烁

根因：ThemeToggle 的 localStorage 读取在客户端 Hydration 之后才执行，
导致 SSR 输出的 HTML 始终为浅色。改为在 <head> 中注入阻塞脚本提前读取。

Closes #7
```

## 8. 代码注释规范

### 8.1 何时写注释

| 需要注释 | 不需要注释 |
|----------|-----------|
| 隐藏约束（性能原因、第三方 Bug 规避） | 复述代码逻辑（`// 遍历文章列表`） |
| 计算中不易理解的数值来源（`// 200ms 阈值对应 CSS 过渡时长`） | 显而易见的操作（`// 返回日期`） |
| 非标准的工作方式（`// Astro 要求 content collection 查询必须 await`） | 类型/函数签名（类型定义本身就是文档） |
| 需要特殊注意的边界情况（`// 处理旧文章没有 updated 字段的兼容情况`） | 标准 API 调用 |

### 8.2 注释风格

```typescript
// ✅ 解释 "为什么"
// Pagefind 的 search() 返回结果中的 url 是相对 dist/ 的路径，
// 需要去除前导 /dist 才能匹配线上 URL
const pagefindUrl = result.url.replace(/^\/dist/, "");

// ❌ 描述 "做了什么"（代码已经说清楚了）
// 把 result.url 中的 /dist 替换为空字符串
const pagefindUrl = result.url.replace(/^\/dist/, "");
```

### 8.3 TODO / FIXME / HACK 标记

```typescript
// TODO: 后续支持按更新时间排序，目前仅按创建时间
// FIXME: 当文章数超过 100 篇时，getCollection 需要加分页
// HACK: Pagefind 的类型定义缺失，临时用 any 绕过，等待 @pagefind/types 发版
```

- `TODO`：计划做的功能增强，非阻塞
- `FIXME`：已知问题/缺陷，需要修复后才能合并
- `HACK`：临时方案，必须在注释中说明为什么不用正规做法

## 9. 错误处理规范

本项目为纯静态站点，**无运行时服务端**。错误处理聚焦于构建时和客户端。

### 9.1 构建时验证

前端数据校验（Content Collections Zod Schema）在 `astro build` 时自动执行，校验失败会导致构建终止。

```typescript
// 构建失败即是一道安全网——错误的 frontmatter 无法上线
// src/content/config.ts 中的 Schema 是唯一的校验关口
```

### 9.2 客户端错误处理

- 搜索失败静默降级：Pagefind 加载失败时显示「搜索暂不可用」，不报错崩溃
- Giscus 加载失败不阻塞页面：评论区域自然降级为「评论加载失败」
- 主题切换失败回退到系统偏好：catch 异常时使用 `window.matchMedia('(prefers-color-scheme: dark)')`

### 9.3 用户体验原则

- 永远不向用户展示原始错误堆栈
- 永远不展示「undefined」「null」「NaN」字样——空值必须使用「暂无」「未设置」等友好占位
- 所有加载中状态必须处理（Skeleton / 占位符），不能出现 UI 跳动

## 11. 依赖管理

### 11.1 安装规范

```bash
# ✅ 正确：使用 pnpm
pnpm add <package>
pnpm add -D <package>      # 开发依赖

# ❌ 禁止：使用 npm 或 yarn
npm install <package>
yarn add <package>
```

### 11.2 依赖审查

引入新依赖前必须满足以下条件：

- **必要性**：功能是否可以通过已有依赖或少量手写代码实现？（优先手写）
- **体积**：是否会显著增加构建产物体积？（使用 `bundlephobia.com` 检查）
- **维护状态**：GitHub 最近 3 个月是否有更新？Issue 响应是否活跃？
- **社区验证**：是否被 Astro 生态广泛使用？（检查 Astro 官方集成列表）
- **零运行时优先**：搜索、样式等应选择构建时方案，不引入客户端 JS 库

### 11.3 版本锁定

- `pnpm-lock.yaml` **必须**提交到 Git
- 依赖版本使用 `^` 前缀（允许小版本和补丁版本自动升级）
- 手动升级依赖时使用 `pnpm update --latest`，不要手动改写 `package.json` 中的版本号

## 12. 环境变量规范

### 12.1 命名规则

| 前缀 | 暴露范围 | 示例 |
|------|---------|------|
| `PUBLIC_` | 构建时内联到客户端 JS（可通过 `import.meta.env` 访问） | `PUBLIC_SITE_URL`、`PUBLIC_GISCUS_REPO` |
| （无前缀） | 仅服务端可用（本项目无服务端，不使用） | 不适用 |

> Astro 约定：客户端可访问的环境变量必须以 `PUBLIC_` 开头，这是框架的硬性安全机制。

### 12.2 文件管理

| 文件 | 用途 | Git 追踪 |
|------|------|----------|
| `.env.example` | 环境变量模板（含注释说明每个变量的用途） | ✅ |
| `.env` | 本地开发环境变量 | ❌ |

### 12.3 安全红线

- **绝对禁止**在代码中硬编码任何密钥、Token、密码
- 新增 `PUBLIC_` 环境变量时**必须同步更新** `.env.example`
- 由于 Astro 的 `PUBLIC_` 前缀变量会暴露到客户端，**不要**在前缀变量中存敏感信息

## 13. AI 协作协议

> 本节定义 AI 辅助开发时必须遵守的规则，确保 AI 生成的代码与人工代码保持一致性。

### 13.1 AI 写代码前必读

| 文档 | 目的 |
|------|------|
| `specs/产品概述.md` | 理解产品定位、核心板块、项目边界，不做超出范围的功能 |
| `specs/技术栈.md` | 确认所用的框架/工具/平台，不引入不兼容的依赖或写法 |
| `specs/项目结构.md` | 确认文件放置位置和模块边界，不把文件放错目录 |
| `specs/开发规范.md`（本文档） | 遵守命名、Lint、提交信息等全部规则 |
| 相关模块的现有代码 | 修改前先读取，保持与已有代码风格一致 |

### 13.2 AI 写代码的规则

| 规则 | 说明 |
|------|------|
| **读后写** | 修改文件前必须先读取该文件，禁止盲改 |
| **最小改动** | 只修改任务要求的部分，禁止"顺便优化"无关代码 |
| **不猜版本** | 安装依赖时使用 `pnpm add` 获取最新版，不手写版本号 |
| **不引入新依赖** | 除非任务明确要求，否则不添加任何新包 |
| **不写无意义注释** | 不写复述代码的注释，只解释"为什么" |
| **不创建多余文件** | 不主动创建 README、文档、配置文件，除非任务要求 |
| **遵循现有模式** | 新增的页面/组件必须与已有文件的写法一致（布局嵌套方式、数据查询模式等） |
| **提交信息规范** | 严格遵循 Conventional Commits，scope 从本规范 7.3 节表格中选择 |
| **不越过项目边界** | 产品概述中明确的「不做」清单，AI 不得擅自实现 |

### 13.3 AI 写完代码后必做

| 步骤 | 操作 |
|------|------|
| **1. 类型检查** | 运行 `astro check` 和 `tsc --noEmit`，确认无类型错误 |
| **2. Lint 检查** | 运行 `eslint .`，确认无 Lint 报错 |
| **3. 格式检查** | 运行 `prettier --check .`，确认格式合规 |
| **4. 依赖方向** | 确认未违反「目录依赖方向速查」中的禁止方向 |
| **5. 环境变量** | 如有新增 `PUBLIC_` 变量，同步更新 `.env.example` |

### 13.4 错题本机制

当 AI 生成的代码出现问题时，记录到 `.ai-fixes/` 目录（按日期分文件）：

```markdown
<!-- .ai-fixes/2026-05-10.md -->

## 错误记录 1
- **错误类型**: 类型错误
- **错误描述**: Astro Content Collections 的 `render()` 返回类型标注错误
- **根因分析**: 未读取 Astro 文档中关于 `render()` 返回类型的最新变更
- **正确做法**: 使用 `CollectionEntry<"blog">` 类型，不手动标注 render 返回值
```

| 记录项 | 说明 |
|--------|------|
| **错误类型** | 类型错误 / 逻辑错误 / 规范违规 / 依赖错误 |
| **错误描述** | 具体出了什么问题 |
| **根因分析** | 为什么会犯这个错 |
| **正确做法** | 下次应该怎么做 |

## 14. 目录依赖方向（速查）

```
合法的依赖方向（自上而下）：

  src/pages/          ← 页面层（路由入口，查询数据）
       ↓
  src/layouts/        ← 布局层（HTML 骨架，通过 Props 接收数据）
       ↓
  src/components/     ← 组件层（UI 片段，通过 Props 接收数据）
       ↓
  src/utils/          ← 工具层（纯函数，无副作用）
       ↓
  src/types/          ← 类型层（纯类型定义）
       ↓
  src/content/config.ts  ← 内容 Schema（基础定义）


允许的横向引用：
  src/pages/*    → src/pages/*       （❌ 禁止：页面不引用其他页面）
  src/layouts/*  → src/layouts/*     （✅ 允许：布局可以嵌套）
  src/components/* → src/components/* （✅ 允许：组件可以组合）
  src/utils/*    → src/utils/*       （✅ 允许：工具函数互相调用）


禁止的依赖方向：
  src/utils/*      ✗→ src/components/*  （工具层不得依赖 UI 层）
  src/types/*      ✗→ 任何非 types 目录 （类型层不得依赖任何其他层）
  src/components/* ✗→ src/layouts/*     （组件不得依赖布局）
  src/components/* ✗→ src/pages/*       （组件不得依赖页面）
  src/content/*    ✗→ src/*             （内容层不引用源码，仅被引用）
```

## 15. 安全编码规范

| 类别 | 规则 |
|------|------|
| **XSS 防护** | Astro 默认对所有 `{expression}` 进行 HTML 转义。如需输出 HTML 使用 `{@html}` 或 `<Fragment set:html>`，且**仅**用于信任内容（如 Markdown 渲染输出）。禁止对用户输入使用 HTML 输出 |
| **密钥管理** | 无服务端，不存在密钥存储问题。GitHub Token 通过 GitHub Actions Secrets 注入，不在代码中引用 |
| **第三方脚本** | Giscus 和 Pagefind 是唯一的外部脚本。禁止引入其他第三方追踪/广告脚本 |
| **外部链接** | 所有外部链接（友链、文章中的外链）必须添加 `rel="noopener noreferrer"` 和 `target="_blank"` |
| **依赖安全** | 定期运行 `pnpm audit` 检查已知漏洞。严重漏洞必须在 24 小时内修复 |
| **内容安全** | Markdown 文章中嵌入的图片使用 Astro 的 `<Image />` 组件优化，避免引用不可信的外部图片 |
